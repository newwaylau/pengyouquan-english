## 技术方案评估

**方案**：SSE（Server-Sent Events）

| 评估项 | 结论 |
|--------|------|
| ✅ 单行道推送 | SSE 天然适合服务端→浏览器的单向推送，无需 WebSocket 复杂度 |
| ✅ Spring 原生支持 | `SseEmitter` 是 Spring MVC 内置类，无需额外依赖 |
| ✅ 自动重连 | 浏览器 `EventSource` 断线后自动重连 |
| ✅ 并发安全 | `ConcurrentHashMap` + `CopyOnWriteArrayList` 保证线程安全 |
| ✅ 可伸缩 | 当前无需持久化，纯内存方案。如果未来需要水平扩展，可改用 Redis Pub/Sub 或消息队列广播 |
| ✅ 安全性 | JWT 验证 + 管理员角色检查在订阅入口完成 |

**无冲突**：不与其他功能共享状态，不影响现有 API 的 REST 接口。

## 潜在优化点（可选，非必须）

1. **SSE 连接数监控**：可以在 `/api/admin/info` 中添加当前 SSE 连接数，方便排查
2. **空闲连接清理**：当前 timeout=0(永不超时)，如果管理员离开页面未正确关闭，连接会永久残留。但 `onCompletion/onTimeout/onError` 回调已正确移除 emitter，浏览器关闭标签页通常会触发这些回调
3. **水平扩展**：如果部署多实例，每个实例的 `ConcurrentHashMap` 是独立的，需要改为 Redis 集中存储
